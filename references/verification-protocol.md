# 验证协议 Verification Protocol

目的：让不认识本 skill 的第三方，能对同一份简历打出**相近分数**并给出可核对的改写建议。

## 1. 准备

1. 加载 `references/common-standards.md` 与目标 `roles/<role>.md`  
2. 确认目标市场（MKT-CN / MKT-US）与是否有 JD  
3. 打开 `bibliography.md` 中将引用的 URL（抽查即可）

## 2. 只评可观察项

对每条标准 ID：先填检查清单（是/否、计数、比例），**禁止**先给印象分再找理由。

记录表字段建议：

| 标准 ID | 检查项结果 | 证据原句（摘录） | 影响维度 |

## 3. 映射到 0–5

使用 `common-standards.md` 中 D1–D7 锚点。规则：

- 取该维度相关标准的检查结果，对照锚点给分  
- **有任一 G-HONEST 硬冲突 → D6 ≤1，并阻断涉事 bullet 的「定稿改写」**  
- G-SCAN-LADDERS 只影响 D1 布局项，**不得单独**把总分压到「科学失败」  
- 角色匹配 D5：`命中` 条数 / `必须证据` 条数；≥80% 可到 5；约 50%→3；&lt;30%→1

## 4. 扣分与改写必须引 ID

对外报告按 `templates/output-template.md` 的四段结构书写。每条优先修改建议必须包含：

1. 唯一编号 `P1`、`P2`、`P3`……（按影响从高到低；禁止多个问题共用同一编号）
2. 白话的「问题」和「为什么要改」
3. 括号中的标准 ID（如 `G-XYZ, AMZ-DATA`），用手册里「为何影响录用」改写成一句人话
4. 原文 / 建议改成 / 需要补充（若有）

标准 ID 写在括号里即可，不要用 ID 替代解释，也不要另开能力对照总表。
无标准 ID 的扣分视为协议违规，需重做。

## 5. 复现实验（建议）

两名审计者独立填写检查表后比较：D1–D7 分差应多数 ≤1；若分差 ≥2，回到检查项而非争论「感觉」。

## 6. 与阶段 2 前端

API 响应中每条 finding 带 `standard_ids: string[]` 与 `evidence_quote`。


## 7. Boss 导出与内容分（1.2.0）

若 MKT-CN-BOSS 噪声高：D4（对外称「系统读取」）可打 1–2，但 **不要**因此自动把 D2/D5 打到 1。内容维度仍按可抽取正文评估。对外说明时写清这是平台导出噪音。

国内投递且 D4 不是明显读取失败时：不要把「系统读取」写入主要不足或高优先级修改。外企 / 明确网申时，再按正常评分项解释。对外解释 ATS 时必须用人话，见 `common-standards.md`「ATS 是什么」。
